# 去 AI 味写作 (deslop-zh)

## 一、核心原则

### 1. 自然 > 风格化
最高优先级：**读起来自然，而非读起来像「努力装人」**。
- 不要为了去 AI 味而硬塞口语词（「说白了」「居然」「谁能想到」「太太太」）
- 不要为「更像人」把技术文改得像口播稿
- 如果原句已经自然、准确、清楚，不改

### 2. 减法优先
去 AI 味是做减法，不是做加法：
- 先删：解释腔、总结腔、防御性叠甲、心理按摩话术、常识性定语堆叠、多余转折、套话填充
- 再调：句式节奏、标点、用词口语化程度
- 不改：代码字面量、URL、API 路径、JSON 键名、数据库字段名

### 3. 保语义 > 去 AI 味
先确认事实、逻辑、因果和历史演进状态不变。
- 为「更口语」或「硬删句式」而改坏原意、丢失上下文 = 失败改写。

### 4. 场景决定策略
不同写作目标有不同标准：
- **技术文档 / 界面微文案 / 代码注释**：克制、准确、可扫读，不用第二人称，不加戏、不安抚
- **博客 / 技术长文**：自然稳重的工程师口吻，不做报告腔也不做口播腔
- **社交媒体**：有性格，有立场，不列功能清单
- **发行说明**：一句话说用户效果，条目密度匹配项目风格
- **科学论文**：保持学术正式度与国标标点，删除空洞套话与夸张状语

## 二、速查清单（写完后过一遍）

- [ ] 段末有「这说明」「可以看出」「到这里」开头的收尾总结句？→ 删
- [ ] 有无病呻吟的否定对比（「不是 X，而是 Y」「不只是 X，更是 Y」「像 X，而不只是 Y」）？→ 删掉虚构靶子 X，直接说结论 Y
- [ ] 有没人质疑却主动撇清的防御性废话（「这只是修改 X，不是重做整个 Y」）？→ 删，只说实际做了什么
- [ ] 有「可 X、可 Y、可 Z」「有 X、有 Y、有 Z」的定语堆叠，或把基础默认属性当卖点？→ 删掉常识项，拆开平实陈述
- [ ] 有「一个 X，N 种 Y」「一次 X，到处/多重 Y」的总分对仗伪口号？→ 改为具体事实说明
- [ ] 注释或界面文案里有「只要你 X，它就立刻 Y，不用 Z」的脑补小剧场？→ 缩减为「点击 X」或「当 X 时执行 Y」
- [ ] 有「主动权始终在你」「随时可以修改/停止」的定心丸式安抚话术？→ 删掉心理按摩，只给客观操作入口
- [ ] 有「随着...的发展」「在当今...时代」开篇套话？→ 删
- [ ] 有「赋能」「抓手」「闭环」「拉通」「沉淀」等黑话？→ 替换为人话
- [ ] 滥用破折号（—— / —）做句中插入解释，或四五个短句连发像打电报？→ 改用逗号/括号，合并短句调整节奏
- [ ] 章节间有「上面这些讲的是...下面我们看...」过渡句？→ 删
- [ ] 有升华句（把具体工程观察上升到普适人生道理）？→ 删
- [ ] 有「一句话总结」「简而言之」等总结标签？→ 删标签，直接说结论
- [ ] 无生命事物做了人类动词（「决策浮现」「数据告诉我们」）？→ 换真人或具体机制做主语
- [ ] 滥用三连排比？→ 换二连或单句直述
- [ ] 自问自答？→ 直接陈述
- [ ] 每个列表项都是 `**加粗关键词**。解释内容` 的机械模式？→ 换格式或用逗号连接

## 三、中文 AI 味模式（核心拦截区）

### 3.1 段末收尾总结句（最高频，优先检查）
一段刚解释完某机制，结尾再重述一遍。

**信号词**：这说明 / 到这里 / 可以看出 / 这本身就是 / 通过以上分析 / 由此可见

> ❌ 「到这里，我们已经看到了内存分配器在 allocation 路径上的三个关键优化点。」
> ✅ 直接删掉，上一句已经说完。

### 3.2 升华句
把具体工程观察上升到普适人生道理。

> ❌ 「这其实和产品设计一样：好的抽象不是为了炫技，而是为了让使用者少犯错。」
> ✅ 直接给具体建议：「所以设计抽象时，先用调用方的视角写一遍调用代码，再决定接口长什么样。」

### 3.3 虚假对比与否定递进（「不是...而是...」及其变体）
AI 极度迷恋通过「踩一个靶子」来抬高结论。只要前一个被否定项（X）不是真实存在的历史状态或读者明确提出的误区，**一律删掉前半句，直接陈述 Y**。

**拦截句式**：
- **基础版**：「不是 X，而是 Y」「不是 X，是 Y」「X 本身没有价值，真正有用的是 Y」
- **彩虹屁递进版（重点拦截）**：「不只是 X，更是 Y」「与其说是 X，不如说是 Y」「它就像一个 X，而不只是一个 Y」

> ❌ 「真正的创新者不是有创意的人，而是五种特质同时拉满的人。」
> ✅ 「真正的创新者是五种特质同时拉满的人。」
>
> ❌ 「这更像创始人筛选框架，不是交易信号。」
> ✅ 「这是一个创始人筛选框架。」
>
> ❌ 「这个 Agent 就像你的私人架构师，而不只是一个代码补全工具。」
> ✅ 「这个 Agent 除了补全代码，还能协助做架构设计。」
>
> ⚠️ **保语义例外**：若 X 是真实发生过的旧状态或排障排除项，不可硬删前半句导致上下文丢失，应改写为时间/状态演进：
> 原句：「性能瓶颈已经不是 I/O，而是锁竞争。」
> ✅ 演进改写：「优化 I/O 后，主要性能瓶颈转移到了锁竞争。」（若原本无 I/O 背景，则直接写「锁竞争是当前的主要性能瓶颈。」）

### 3.4 无端防御与边界撇清（「谁问你了」综合征）
禁止在用户没有质疑时，为了维护语言边界而主动叠甲、撇清免责。

**信号词**：这只是...不能当成... / 我们只是...不是要重做... / 需要明确的是，它并不能替代...

> ❌ 「我们只是修改系统的这几个功能模块，不是重做整个系统。」
> ✅ 「接下来我们修改这几个系统功能模块。」
>
> ❌ 「这个指标只是反映当前的离线测试表现，不能当成最终的线上效果承诺。」
> ✅ 「该指标反映模型在离线测试集上的表现。」

### 3.5 定语堆叠与「一与多」伪口号
禁止把事物的默认基础属性包装成排比卖点，禁止滥用总分对仗的营销结构。

- **剥离常识定语三连**：不说「可编辑、可定制、可追溯的数据库」（数据库默认即可编辑），不说「有表情、有动作、有脾气，真正懂你」。删掉凑数的常识项，只写独特机制。
- **禁用「一与多」总分结构**：禁用「一个程序，N 种命令」「一次配置，多重收益」「一个底座，全场景覆盖」等套路化对仗。

> ❌ 「我们构建了一个可配置、可扩展、可追溯的日志模块，一次接入，多处排查。」
> ✅ 「该日志模块支持动态调整采样率，并提供统一的链路 ID 用于跨服务排查。」

### 3.6 脑补小剧场（注释与微文案过度叙事）
在写代码注释、UI 按钮文案、配置说明或条件分支时，克制「讲故事（elaborate）」的冲动，不用「只要...立刻...不用...」脑补动态过程。

> ❌ 按钮注释：「你一点击这个按钮，它就立刻回应，不用漫长等待。」
> ✅ 按钮注释：「点击回应。」
>
> ❌ 条件说明：「只要上游服务一出现超时，熔断器就会立刻介入切断请求，不用担心系统被拖垮。」
> ✅ 条件说明：「当上游服务超时率达到阈值时，熔断器切断请求以防级联故障。」

### 3.7 强塞定心丸（过度安抚腔）
不要把用户预设为极度焦虑、缺乏安全感的弱者。禁止在代码注释、界面提示和技术文档中塞入心理按摩话术。

**禁用词**：主动权始终在你 / 完全由你掌控 / 随时可以修改 / 随时可以停止 / 放心尝试 / 哪怕出错也随时能撤回

> ❌ 「系统会自动生成初始配置，但主动权始终在你手里，你随时可以修改，也随时可以停止。」
> ✅ 「系统生成初始配置后，可在设置页手动修改或中止任务。」

### 3.8 讲解腔 / 训人感起手
> ❌ 「真拆开看...」「这背后是同一个变化...」「真正关键的问题是...」
> ❌ 「先问问是不是」「你要先明白」
> ✅ 直接说。「先确认...」「可以先看...」

### 3.9 总结腔标签
不要在结尾前加总结标签。

> ❌ 一句话总结 / 简而言之 / 概括来说 / 总而言之 / 综上所述 / 总结一下 / 一句话落地 / 一句话讲
> ✅ 直接给结论（punchline），不加标签。

### 3.10 文章开篇套话
> ❌ 「随着 AI 技术的不断发展...」「在当今数字化浪潮中...」「近年来，XXX 受到了越来越多的关注...」
> ✅ 直接开头。「用了不到一个月后...」「先说结论...」「这次想把 X 这条链路讲清楚...」

### 3.11 中文黑话与虚浮附加
以下词默认不用（除非引用原文或行业固定术语）：
- **绝对禁用**：赋能、抓手、闭环、沉淀、对齐、对标、拉通、打通、协同、联动、洞察、赛道、心智、调性、战役、链路、势能、兜底
- **谨慎使用**：场景、生态、体系、路径、触点、卡点、布局、矩阵、颗粒度、复盘、梳理、输出、提炼

> ❌ 「通过数据沉淀赋能业务闭环」
> ✅ 「积累数据后，业务能形成完整流程」

额外警惕：
- **过度强调重要性**：对普通主题用「至关重要」「意义重大」「关键时刻」「转折点」→ 删
- **过度列举来源**：「依据多家媒体报道...」「显示其于产业中具一定能见度」→ 删
- **表面分析附加**：用分词短语附加空洞评论，如「反映了当代社会的变迁」→ 删或给具体证据
- **推广语气**：「文化遗产」「文化底蕴」「自然之美」→ 删
- **模糊归因**：「据业内人士指出」「有评论认为」→ 要么说清谁说的，要么不说
- **展望章节套话**：「尽管（主题）有其意义，但其面临的挑战有...」→ 具体说问题，不给虚无展望

### 3.12 翻译腔套路与假主体
> ❌ 「接住」「击穿」「锋利」「不崩」「不爆」「打穿」「扛住」等物理动作动词用在了抽象认知上
> ✅ 换成日常中文：「你这几条我都收到了」「这个假设不成立」
>
> ❌ 抽象名词或无生命事物做主语：「工程上的现实比这些数字难看」「数据告诉我们」「决策自然浮现」
> ✅ 重写，用具体的人、系统模块或动作做主语。

### 3.13 空泛形容词预判
> ❌ 「更干净：xxx」「逻辑很清晰：xxx」
> ✅ 删掉形容词预判，直接说 xxx。

### 3.14 句式节奏与排版惯性
- **三连排比**：一个三连可以，背靠背的三连是模式识别失败 → 换二连或单句
- **机械序列**：用「首先...其次...最后」？→ 换「一方面...另一方面...」或直接分段
- **电报短句**：四五个短句（句号）连发像打电报？→ 合并长句或用逗号连接，拉出长短句节奏变化
- **加粗句号模式**：列表项 `**xxx**。content` → 改为 `**xxx**，content`（或自然融入段落），让加粗词成为句子承重成分而非生硬的独立小标题

### 3.15 标点与中英留白（分场景适用）
- **引号**：技术博客、技术文档优先使用直角引号 `「」`『』；**科学论文、正式出版物、政企公文**遵循国标使用弯引号 `“”`‘’
- **破折号**：禁止模仿英文 em-dash（— 或 ——）在句中充当括号或冒号插入解释说明，一律改用逗号、分号或括号
- **感叹号**：默认不用（除非推文/社交场景且确有强烈情绪）
- **中英留白**：
  - **技术文档、博客**：中文与英文/数字之间加空格（如 `版本 2.0`、`调用 API 接口`）
  - **社交媒体 / 短消息**：不强制加空格，顺应真人自然打字习惯
  - **绝不加空格的对象**：代码块、JSON 键名、URL、内联代码

### 3.16 第二人称控制
- **技术文档 / 论文 / 注释**：禁用「你」「您」。用「开发者」「调用方」等角色词，或直接用无主句/祈使句
- **博客**：可以用「你」，但不要通篇「你会发现」「你需要」「你可以看到」

## 四、分场景策略

### 4.1 技术文档 / API 文档 / 界面微文案 / 代码注释
**触发**：「技术文档」「API 文档」「产品文案」「界面文案」「帮助文档」「注释」

- 语气：克制、直接、可扫读
- 不用第二人称（「你」「您」）
- 不用「领先」「强大」「重磅」「颠覆」「震惊」「炸裂」等宣传形容词，不堆叠「可 X、可 Y、可 Z」
- 注释与按钮文案直奔主题，严禁「脑补小剧场」（3.6）和「强塞定心丸」（3.7）
- 不用「赋能」「抓手」「闭环」等黑话，不用感叹号，使用直角引号 `「」` 并保持中英留白
- 不改代码字面量、JSON 键名、URL、API 路径
- 术语首次出现标注，后续不重复解释；不用「Hello」「Hi」等问候开篇
- 目标：说清楚「它是什么、用来做什么、下一步看哪里」

### 4.2 技术博客 / 长文
**触发**：「博客」「技术文章」「技术长文」「写一篇」「科普」

- 默认模式：资深工程师给同事讲系统的口吻，可以口语，但不俚语化
- 减少情绪词、感叹词、口头禅；少用「说白了 / 其实 / 你会发现 / 谁能想到」推进行文
- 优先追求：清楚、稳、具体、节奏自然
- 优先做减法：删解释腔、删总结腔、删无端防御（3.4）、删多余转折；若原句自然则不改
- 非工程师受众：先去「不懂技术的同学」等居高临下词，去「你必须」等训人腔，去太深术语。走「我怎么用的，你试试」路径，不走「系统综述 + 框架表 + 长分析段落」

### 4.3 社交媒体 / 推文
**触发**：「推文」「X推文」「twitter」「社交发文」「post」

- **通用规则**：
  1. **一条立场**：至少一句表明真实看法或决策原因的意见句
  2. **拒绝大纲**：不列功能清单、不用「一个 X，多个 Y」口号、不强加中英空格
  3. **中文节奏**：用地道表达，避免翻译腔和正式书面词，结尾用自然交流而非生硬 CTA
- **若是「产品/开源项目发布」推文**：
  1. **社区先行**：开头用社区锚点（star 数、感谢用户、谁的反馈推动），改动放后面
  2. **亮点不全量**：挑 2-4 个最有意思的点讲故事，不当 changelog
  3. **用户感受帧**：用「用它的时候...」「有一种...的感觉」，而非「该工具实现了...」
- **公开前扫三件事**：身份与敏感信号脱敏、不踩竞品、感受先于清单

### 4.4 发行说明 / Release Notes
**触发**：「release」「changelog」「版本」「发行说明」

- 结构：Breaking Changes → New Features → Fixes & Improvements → Deprecations
- 格式：优先匹配目标项目最近一次 release 风格
- 条目：5-8 条，每条约一句话，只说用户可感知的实际效果，不写脑补小剧场
- Title：版本号 + 最核心改动或主题，不超过 10 个词
- 不要加 emoji（除非项目本身庆祝风格）
- 不加「不再更新」「final release」「停止维护」等终止信号（除非真实情况）
- 中英双语：条目一一对应，不混写，英文在前

### 4.5 科学论文 / 学术写作
**触发**：「论文」「abstract」「cover letter」「grant」「manuscript」

- 保持学术正式度与国标标点（弯引号 `“”`），严禁套用口语词汇替换表（保留「使用」「例如」「实验结果表明」等标准学术用语）
- 删除空洞套话与夸张修辞：不用「在当今日新月异的领域中」「长期以来人们认识到」「这一范式转变具有深远意义」「值得注意的是」
- 用「我们」或「本文」指代自身工作，不用被动语态躲闪
- 引用具体作者与年份，不用「有研究者指出」「据观察」
- 给出具体实验数字与对比幅度，而非空泛定性结论

### 4.6 双语内容
**触发**：「双语」「中英」「bilingual」「翻译」

- 中英字符间加空格；不混用标点（中文用全角标点，英文用半角标点）
- 术语跨全文一致：首次出现保留英文 + 中文注解（或中文前置 + 英文括注），后续只用中文
- 常见可替换：context→上下文、state→状态、cache→缓存、claim→断言、runtime→运行时
- 术语未收敛的（prompt、embedding、tokenizer、Agent）保留英文
- 双语版：条目编号一一对应，确认 EN/CN 意思一致，标记翻译损失；禁止破折号插入语

## 六、执行流程

1. **先定模式与场景**：
   - **默认改写模式**：识别场景（博客/技术文档/注释/推文/论文），直接执行改写。
   - **审稿检查模式**（当用户明确要求「审稿」「检查 AI 味」「挑刺」且不要求直接重写时）：不直接覆盖全文，按列表输出命中的规则编号、原句摘录与修改建议。
2. **先保语义**：确认事实、因果与历史演进背景不被删丢。
3. **做减法（按优先级清扫）**：
   - 一扫段末总结句（3.1）与开篇套话（3.10）
   - 二扫虚假对比、彩虹屁递进（3.3）与「谁问你了」式无端防御（3.4）
   - 三扫定语堆叠、「一与多」伪口号（3.5）、脑补小剧场（3.6）与强塞定心丸（3.7）
   - 四扫黑话、空洞形容词预判（3.11, 3.13）与假主体（3.12）
4. **再顺句子**：调整长短句节奏、修正破折号与引号、处理中英留白。
5. **最后回读**：优先修不自然处，绝不强改已经自然的句子。
6. **输出**：默认改写模式下，**只输出改写后的文本**，不加改动清单、解释或寒暄收尾话（除非用户明确要求）。

## 七、改写示例

### 示例 1：中文技术博客
**改写前：**
> 众所周知，随着云原生技术的不断发展，Kubernetes 已经成为了容器编排领域的事实标准。值得注意的是，虽然 K8s 本身功能强大，但在实际落地过程中，很多同学会发现它并不是银弹。本文将从多个维度深入探讨企业在落地 Kubernetes 时面临的挑战和应对策略，希望能为正在考虑或已经踏上云原生之旅的各位带来一些启发。

**改写后：**
> 我们团队用 Kubernetes 跑了三年生产环境。最大的感受：K8s 解决了部署问题，但把复杂度转移到了别的地方。这篇文章记录我们踩过的五个坑，以及每个坑的止损方案。

### 示例 2：技术文档
**改写前：**
> 你好！欢迎使用我们的 API 服务！我们的平台提供领先的、强大的数据处理能力，能够赋能您的业务，助力您在数字化转型的赛道上实现弯道超车。使用前，您需要先进行 API Key 的申请。

**改写后：**
> API 提供以下数据处理能力：批量查询、实时推送、数据清洗。调用前需先申请 API Key，详见「认证」章节。

### 示例 3：对比句式修复（区分修辞靶子与真实演进）
**改写前（无病呻吟靶子）：**
> 微服务架构的价值不在「微」，而在于边界清晰。它就像一把精准的手术刀，而不只是一个代码拆分工具。

**改写后：**
> 微服务架构的核心价值在于边界清晰。

**改写前（真实排障演进）：**
> 经过昨晚的压测，系统的性能瓶颈已经不是 I/O，而是锁竞争。

**改写后：**
> 昨晚压测排查发现，I/O 瓶颈解除后，当前的性能瓶颈转移到了锁竞争。

### 示例 4：空洞套话净化
**改写前：**
> 从多个维度来看，Redis 在高并发场景下具有至关重要的意义。不仅能够提升系统响应速度，还对整体架构的可扩展性产生了深远影响。

**改写后：**
> Redis 用单线程模型处理读写，省去了锁开销。我们压测发现，相同硬件下 Redis 的 QPS 比 MySQL 高两个数量级。

### 示例 5：新一代 AI 味综合净化（堆叠定语 + 小剧场 + 防御撇清 + 定心丸）
**改写前：**
> 我们开发了一个可编辑、可定制、可追溯的本地配置模块，一次编写，到处生效。需要注意的是，这只是对配置读取逻辑的局部优化，不是重做整个后端系统。在界面上，你只要一点击「同步」按钮，系统就会立刻应用新配置，不用漫长等待。而且主动权始终在你手里，你随时可以修改参数，也随时可以停止同步。

**改写后：**
> 本次更新调整了本地配置模块的读取逻辑，支持自定义配置模板与变更历史记录。点击界面上的「同步」按钮即可应用新参数；同步过程中可在设置页修改参数或中止任务。

## 八、质量评分（可选用）

五个维度，每维 1-10 分，低于 35/50 需重新过一遍减法流程：

| 维度 | 检验问题 |
